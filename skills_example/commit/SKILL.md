# Git 提交助手

目标：产出一个**粒度合适、信息准确、格式规范**的提交。提交信息是写给半年后的自己看的——它要能独立回答"这次改动做了什么、为什么这么做"。

## 核心原则

1. **一次提交只做一件事**。一个功能点 + 顺带的必要小修可以接受；功能开发与格式化扫荡、无关重构混在一起不可以。发现混杂时，建议用户分批提交（`git add -p` 或按文件分组）。
2. **信息必须来自证据**。标题和正文都要从 diff 中归纳，不要照抄用户的口头描述——用户说"修了个 bug"，diff 里可能是三个不相关的改动。
3. **提交前必须检查暂存内容**。永远先 `git diff --cached`（或将要 add 的文件），确认没有不该进仓库的东西。

## 流程

### Step 1: 摸清现场

```bash
git status          # 有哪些改动、在哪个分支
git diff            # 未暂存的改动
git diff --cached   # 已暂存的改动
git log --oneline -5  # 本仓库的提交风格基线
```

### Step 2: 确定提交范围

- 改动已全部暂存 → 直接进入 Step 3
- 改动未暂存 → 询问用户是全量提交还是部分提交；部分提交时按逻辑单元分组 add
- 存在未跟踪文件 → 逐个判断是否该入库（见下方排除清单），不确定的问用户

**排除清单**（发现即提醒用户，除非用户明确要求）：
- 密钥/凭据：`.env`、`*_secret*`、token、password 字样
- 本地杂项：`.DS_Store`、`*.log`、编辑器临时文件
- 编译产物：`bin/`、`dist/`、`vendor/`（除非项目明确提交 vendor）
- 大文件：单个超过 1MB 的非源码文件

### Step 3: 归纳提交信息

格式遵循 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/)，描述用中文（与仓库历史风格一致）：

```
<type>(<scope>): <一句话概括，祈使语气，不超过 50 字>

[可选正文：为什么改、怎么改的、影响范围，每行不超过 72 字]
```

**type 选择**：

| type | 用途 |
|------|------|
| feat | 新功能 |
| fix | 修 bug |
| refactor | 重构（不改行为） |
| test | 补/改测试 |
| docs | 只改文档 |
| chore | 构建、依赖、配置等杂项 |
| perf | 性能优化 |
| style | 格式调整（不影响逻辑） |

**scope**：改动集中的模块/包名，如 `engine`、`tui`、`skill`。跨多个模块且无主次时省略 scope。

**判断要点**：
- 标题写"做了什么"，不写"改了哪些文件"
- 正文回答"为什么"：动机、方案取舍、潜在的兼容性影响
- 含破坏性变更时，正文首行写 `BREAKING CHANGE: <说明>`
- 修复了某个 issue 时在正文引用，如 `Closes #12`

### Step 4: 提交

1. 先把拟好的提交信息**展示给用户确认**，用户点头后再执行
2. 提交信息用 heredoc 传入，避免引号转义问题：

```bash
git commit -m "$(cat <<'EOF'
fix(engine): 修复会话恢复时上下文丢失

恢复会话时直接复用了上一轮的消息列表，导致压缩后的
摘要没有落库。改为恢复前强制读取会话存储的最新快照。

Closes #10
EOF
)"
```

3. 提交后 `git log -1 --stat` 验证内容与预期一致，向用户报告提交哈希和文件数

## 禁止事项

- **永远不要**在未经用户确认的情况下执行 `git push`。提交和推送是两个动作，本技能只负责前者。
- **永远不要**用 `git add -A` 一把梭——逐文件或按组 add，先看内容再进暂存区。
- **永远不要**使用 `--no-verify` 跳过 git hooks，除非用户明确要求并知晓后果。
- 不伪造未发生的改动（如 diff 为空时拒绝提交，向用户说明）。
