# 系统性调试

目标：找到**根因**并修复它，而不是让症状消失。每一次"改一行试试"而没有假设验证的尝试，都是在随机搜索——搜索空间稍大就必然失败。

## 铁律

1. **先复现，再动手**。不能稳定复现的问题，先构造复现条件（最小输入、特定时序、并发压测）。改不了复现路径的问题，你无法知道它有没有被修好。
2. **每次只改一个变量**。同时改两处，即使好了你也不知道是哪一处起效。
3. **修根因，不修症状**。加 `if err != nil { return nil }` 让报错消失，问题只是被搬到了更难查的地方。
4. **失败信息是证据，读完它**。panic 栈、错误串、测试输出——逐行读完之前不做任何假设。

## 流程

### Step 1: 复现并固化

- 跑一遍让问题出现的命令/测试，确认能稳定复现
- 不稳定复现时：并发问题跑 `go test -race -count=10`；时序问题加日志/断言缩小窗口
- 把复现路径写下来（命令 + 期望行为 + 实际行为），这是后续所有判断的基准

### Step 2: 收集证据，形成假设

按成本从低到高：

1. **读错误信息全文**。panic 的第一行和栈顶；错误链 `errors.Wrap` 的每一层
2. **读相关代码**。沿着栈/调用链读，注意和直觉不符的地方
3. **加观测**。在可疑位置加临时日志或单步断点，打印中间状态
4. **二分定位**。注释掉一半逻辑 / 逐步缩小输入，看问题何时消失

每收集一轮证据，显式写下当前假设："我怀疑是 X，因为证据 Y；如果是 X，那么改动 Z 应该让症状变化为 W"。**假设要可证伪**——想不出验证办法的假设没用。

### Step 3: 验证假设，锁定根因

- 做一个能区分"是根因"和"碰巧"的实验：直接触发/阻止假设的条件，观察症状是否如预期出现/消失
- 多层因果时往下再问一层："为什么这个值会是 nil？"——直到到达一个改掉它问题就消失、且能解释所有症状的点
- 在向用户报告前，确认根因能解释**全部**观察到的症状。解释了一半的根因通常是另一半问题的邻居

### Step 4: 设计修复

- 修复点尽量靠近根因，远离症状
- 修复前先写一个**会失败**的测试（复现该 bug 的用例），再修到它通过——否则无法证明修复有效
- 评估波及面：同样模式在别处还有吗？`grep` 类似调用点，一并确认
- 如果正确的修复代价大（需要重构），向用户说明，先给最小安全修复 + 后续方案，不要擅自扩大战场

### Step 5: 验证与收尾

```bash
go build ./...        # 编译通过
go test -run TestBugXxx -v   # 新增的回归测试通过
go test ./... -race   # 全量回归 + 竞态检查通过
```

- 删掉调试期间加的临时日志
- 向用户报告：根因是什么（一句话 + 证据链）、怎么修的、新增了什么回归测试、还有哪些类似风险点

## 常见 Go 陷阱速查

遇到症状先对照这张表，命中率很高：

| 症状 | 高频根因 |
|------|---------|
| nil pointer panic | map 未初始化就写、结构体指针字段未赋值、接口持有 nil 指针 |
| goroutine 泄漏 / 卡死 | 向无接收者的 channel 发送、缺 ctx 传播、WaitGroup 计数不匹配 |
| 偶发数据竞争 | slice/map 非并发安全却被共享、`sync.Mutex` 值拷贝 |
| race detector 报警但平时正常 | 正是并发 bug，不要用"加个 sleep"掩盖 |
| defer 不执行 | panic 在 defer 注册前发生、循环内 defer 延迟到函数结束 |
| 测试单独跑过、全量跑挂 | 用例间共享全局状态/工作目录/环境变量 |
| 时间相关偶发失败 | 依赖真实时钟的时序假设，注入固定时钟 |

## 禁止事项

- 不在没复现的情况下直接改代码
- 不用空 catch / 忽略错误的方式"消除"报错
- 不为了过测试改断言值（除非确认是断言本身写错了，并说明理由）
- 不在同一轮里叠加多个"可能有用"的修改
