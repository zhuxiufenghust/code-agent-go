# Go 代码重构

目标：**行为不变，结构变好**。重构的前提是安全网——没有测试覆盖的代码先补测试再动刀，否则"行为不变"只是愿望。

## 核心原则

1. **小步前进，每步可验证**。一次只做一个重构手法，做完立刻 `go build && go test`。大爆炸式重写不是重构，是赌博。
2. **不改公开契约**。导出函数的签名、行为语义、错误类型保持不变；确实需要破坏性变更时停下来和用户确认，那是另一个任务。
3. **消除重复优先于增加抽象**。两次重复可以容忍，第三次出现再抽象（Rule of Three）。为"未来可能的需求"提前设计的抽象，几乎都会变成负资产。
4. **每次提交一个语义**。重构提交不混入行为修复，行为修复不混入重构——让 `git bisect` 和 CR 都有的放矢。

## 流程

### Step 1: 建立安全网

1. 确认目标代码有测试覆盖；没有的话先按 test 技能的方法补齐关键路径测试
2. `go build ./... && go test ./...` 全绿，记下基线
3. 跑 `go vet ./...`，记录已有告警（区分"本来就有的"和"重构引入的"）

### Step 2: 找到坏味道

对照清单扫描目标代码，按收益排序处理：

| 坏味道 | 处理手法 |
|--------|---------|
| 函数过长 / 嵌套过深 | 提取函数；卫语句前置，让正常路径左对齐 |
| 重复代码块 | 提取公共函数/方法，参数化差异点 |
| 一函数多职责 | 拆分；让每个函数名字能准确说清它做的那一件事 |
| 参数列表过长 | 收拢为 options 结构体或 config 类型 |
| 注释在解释"代码在干什么" | 好代码让注释失业；删掉解释性注释，保留"为什么"注释 |
| 魔法数字/字符串 | 提取为具名常量 |
| interface 过胖 | 按使用方拆成小接口（接口定义在使用方） |
| 错误处理重复 | 提取错误包装辅助函数 |

**不处理**的：与本次目标无关的既有混乱（记下来告知用户，不顺手扩大战场）、自动生成代码、纯风格问题（交给 gofmt/gofumpt）。

### Step 3: 执行重构循环

对每一处改动重复：

```
1. 应用单一手法（提取/内联/移动/重命名）
2. go build ./...        —— 编译过
3. go test ./受影响的包/  —— 行为没变
4. 检查调用方            —— 没有遗漏的引用
5. 提交（或暂存）这一步
```

**重命名**注意：导出标识符的重命名是 API 变更，先全仓库 `grep` 所有使用点再动手。
**移动代码**注意：跨包移动要处理 import 循环；出现循环说明包边界划错了，先和用户讨论包结构。

### Step 4: 收尾验证

```bash
gofmt -l . 或 gofumpt -l .   # 格式无漂移
go vet ./...                  # 无新增告警
go test ./... -race           # 全量回归 + 竞态
```

### Step 5: 汇报

向用户报告：
- 做了哪些重构（按手法列出，附文件:行号）
- 删掉了多少行、净变化是多少
- 行为不变的验证依据（测试结果）
- 发现但未处理的问题清单（含建议）

## 禁止事项

- 不在没有测试安全网的代码上做结构性重构（先补测试）
- 不顺手"优化"无关代码
- 不在重构提交里夹带行为变更或依赖升级
- 不引入新抽象除非眼前就有 ≥2 处使用
- 导出 API 的签名变更必须先征得用户同意
